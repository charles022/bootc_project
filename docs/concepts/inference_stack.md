# Inference stack

## What

A single host-managed vLLM container provides OpenAI-compatible inference to every tenant agent. The service runs as a Quadlet (`vllm.container`) attached only to a private podman network (`vllm-internal`) that has no default route. Agents reach it as `http://vllm:8000/v1`. Authentication is a single shared API key generated on first boot into `/etc/openclaw-platform/vllm.env` and distributed per-tenant through `openclaw-broker` + `credential-proxy`.

## Why

The host has one GPU. Running one shared vLLM maximises VRAM utilisation and KV-cache reuse. The alternative — one vLLM per tenant — multiplies VRAM cost and is rarely viable on a single workstation GPU.

The trade-off: tenants share an inference queue. We mitigate, not eliminate, with vLLM's built-in `--max-num-seqs` and `--gpu-memory-utilization`. Per-tenant rate quotas are out of scope for the minimal design and would require an auth proxy.

## How isolation is enforced

Three layers, in order:

1. **Network.** `vllm-internal.network` declares `Internal=true`, so vLLM has no path to the public internet and is not reachable from the host's default network. Agent pods attach to `vllm-internal` via `Network=vllm-internal.network` in `agent.pod.tmpl`.
2. **Authentication.** vLLM is launched with `--api-key ${VLLM_API_KEY}`. The key is generated by `vllm-bootstrap.service` on first boot and stored in `/etc/openclaw-platform/vllm.env` (mode 0600, root-only). Agents do not see this file. Per-tenant grants are issued through `openclaw-broker`: an operator runs `platformctl credential put <tenant> vllm $(grep ^VLLM_API_KEY= /etc/openclaw-platform/vllm.env | cut -d= -f2)` and then `platformctl grant <tenant> <agent> vllm`. Inside the pod, the agent runtime requests credential id `vllm` from `credential-proxy`, which forwards to the broker. Without a grant, the agent has network reachability but no key.
3. **Process hardening.** vLLM runs `ReadOnly=true`, `NoNewPrivileges=true`, `DropCapability=ALL`, `/tmp` and `/dev/shm` on tmpfs, model cache on a dedicated named volume.

## Threat model and known limits

| Concern | Mitigation | Residual |
|---|---|---|
| Tenant agent calls vLLM without permission | Broker grants gate access to the API key | If an operator manually grants the key, that grant is hard to revoke retroactively for in-flight requests |
| Tenant agent exfiltrates data via vLLM endpoint | `vllm-internal` has `Internal=true`; no public egress | A tenant who already has the key can submit any prompt; vLLM is not a data filter |
| One tenant starves another | `--max-num-seqs`, `--gpu-memory-utilization` | No per-tenant fair queuing; consider an auth proxy if it becomes necessary |
| Tenant A scans tenant B's pod on `vllm-internal` | Agent runtimes have no listening sockets — they are outbound HTTP clients only | Future work: per-tenant network with a userland proxy bridging to vLLM |
| Compromised vLLM container escapes to host | Read-only rootfs, dropped caps, no privilege escalation, no host PID/IPC | GPU access via CDI is the highest-trust surface; follow the GPU stack hardening notes |

## Implications

- **The host owns inference.** It is a host service like SSH or the broker, not a tenant workload. Quadlet manages lifecycle.
- **The model choice is host policy.** Operators set `VLLM_MODEL` in `/etc/openclaw-platform/vllm.env`. Tenants cannot pick.
- **Agents speak OpenAI.** The runtime template sets `OPENAI_BASE_URL=http://vllm:8000/v1` and `OPENCLAW_INFERENCE_CREDENTIAL_ID=vllm` so any OpenAI-SDK client works once the credential is granted.
- **No SSO with the model.** Treat the model as a shared library: capable, but assume it sees prompts from many tenants. Do not pass keys to it expecting privacy.
